# 公開データモデル

## 目的

`docs`を正本として、承認済み内容だけを将来の`src/data`へ表示用コピーとして格納するためのルールを定義する。

## 正本と表示用コピー

- 大会ルール、キラー制限、MAP、ポイント制度の正本は`docs`とする。
- `src/data`は公開承認済み内容の表示用コピーとする。
- `src/data`を根拠に`docs`の仕様を変更しない。
- 両者が矛盾する場合は表示用コピーの更新を停止し、ユーザへ確認する。

## データ化の承認フロー

1. 関連する`docs`を確認する。
2. 確定、検討中、未定、運営メモを分類する。
3. 文書間の矛盾を確認する。
4. 公開文言、状態、公開可否をユーザが承認する。
5. 承認済み内容だけを`src/data`へ転記する。
6. 元文書と更新日を記録する。
7. 画面表示と`docs`を照合する。

Markdown草案からの自動変換は初期構成に含めない。

## サイト・大会シリーズ・開催回

サイト、イベントシリーズ、開催回は別の概念として扱う。

| 概念 | 責務 | 現在の名称 |
|---|---|---|
| `site` | イベントポータル全体を識別する | そらふぇす |
| `eventSeries` | サイト内で継続開催する大会シリーズを識別する | ふろぐCup |
| `eventEdition` | シリーズ内の個別開催回を識別し、その回のルールや公開情報と関連付ける | ふろぐCup Vol.1 |

- `site`、`eventSeries`、`eventEdition`を同じ名称項目へ統合しない。
- 将来、ふろぐCup Vol.2、ふろぐCup Vol.3を追加できる構造を前提とする。
- ルールや変更履歴は、対象となる開催回を識別し、開催回ごとの差分を管理できる前提とする。
- 名称体系の正本は`docs/requirements/event-naming.md`とする。
- 現時点では概念モデルだけを定義し、実装ファイルやTypeScript型は作成しない。
- 開催回IDの具体形式は将来検討とする。
- 派生大会・エンジョイ大会は将来検討であり、現在のモデルへ公開対象として追加しない。

## 共通メタデータ

概念上、公開データは以下の共通情報を持つ。

```ts
interface PublicContentMeta {
  status: ContentStatus;
  isPublished: boolean;
  sourceDocuments: string[];
  updatedAt?: string;
  version?: string;
  note?: string;
}
```

実際の型定義は実装フェーズで確定する。

## ContentStatus

初期候補は以下とする。

```ts
type ContentStatus =
  | "confirmed"
  | "under-review"
  | "planned-change"
  | "undecided";
```

| 値 | 意味 |
|---|---|
| `confirmed` | 確定済み |
| `under-review` | 検討中 |
| `planned-change` | 現在有効だが変更予定 |
| `undecided` | 内容が未定 |

使用可否は確定状態とは別の概念であるため、必要なデータでは次を別フィールドとして持つ。

```ts
type Availability =
  | "allowed"
  | "banned"
  | "conditional"
  | "undecided";
```

## isPublished

- `true`: 状態を明示したうえで公開してよい。
- `false`: 公開画面へ表示しない。
- `status`が`confirmed`でも、公開承認がなければ`false`とする。
- `status`が`under-review`でも、検討中としての公開承認があれば`true`にできる。

画面側は`isPublished: false`の項目を表示対象から除外する。

## ルールデータ

ルールデータは次の情報を分離して保持する。

- ID
- カテゴリ
- タイトル
- 公開文言
- 条件
- 例外
- 状態
- 公開可否
- 根拠文書
- 更新日またはルール版

禁止、条件、例外を1つの自由文だけにまとめない。

## キラーデータ

キラーデータの候補項目:

- ID
- 表示名
- 確定状態
- 使用可否
- パーク制限
- アドオン制限
- MAP制限
- フックボーナス
- 補足
- 公開可否
- 根拠文書

ポイントをキラーデータ内へ重複保持するか、ポイントデータから参照するかは未決とする。

## MAPデータ

MAPデータの候補項目:

- ID
- 表示名
- 室内・屋外・未定の区分
- 確定状態
- 使用可否
- 使用条件
- 関連するキラー制限
- 補足
- 公開可否
- 根拠文書

候補MAPを確定MAPとして扱わない。

## ポイントデータ

ポイントデータの候補項目:

- ID
- 対象種別
- 対象ID
- ポイント値
- 適用条件
- 確定状態
- 公開可否
- 根拠文書

未定の数値には`0`を使用せず、値なしとして扱う。`0ポイント`と`未定`を区別するためである。

## 変更履歴データ

将来の変更履歴には次を記録する。

- 変更日
- 対象ID
- 変更概要
- 変更理由
- 適用開始日
- 根拠文書

変更履歴の表示場所は未決とする。

## ID命名規則

- IDは英小文字、数字、ハイフンを基本とする。
- 表示名を変更してもIDは変更しない。
- キラー、MAP、ルール間で同一IDを使い回さない。
- ゲーム内名称の揺れや通称は表示名・別名として扱い、IDには使用しない。

## 日付とバージョン

- 日付は`YYYY-MM-DD`形式を基本とする。
- ゲームバージョンやチャプター範囲に依存する場合は確認対象を記録する。
- 更新日が不明な草案へ推測の日付を付けない。

## 非公開データの扱い

- 運営メモを公開データへ含めない。
- 非公開項目をブラウザへ配信しない設計を優先する。
- `isPublished: false`だけに依存して機密情報を同じ配列へ保持しない。
- 将来、公開用と運営用を分ける必要が生じた場合は別データ境界を設計する。

## 文書間矛盾時の扱い

- 実装者が優先順位を推測しない。
- `docs/issues/open-decisions.md`へ矛盾を記録する。
- ユーザの決定後に正本を更新してから公開データへ反映する。
- 既存の「同一キラー使用不可」と「重複使用ポイント加算」の矛盾は未決事項として扱う。

## 検証項目

- 公開データの各項目に根拠文書がある。
- 非公開項目が画面へ表示されない。
- 検討中と確定が区別される。
- 使用禁止と検討中が別の軸で表現される。
- 数値の未定と0が区別される。
- `docs`と公開文言に意味の差がない。

## 未決事項

- 開催回ごとのルール差分の保持方法
- `ContentStatus`の最終列挙値
- ポイント情報の正規化方法
- 更新履歴の保存単位
- 公開用データファイルの分割方法
- 初期`RulesPage`へ転記する項目
