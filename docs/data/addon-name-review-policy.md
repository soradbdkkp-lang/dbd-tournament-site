# アドオン日本語名レビューポリシー

## 目的

アドオンの日本語名候補を、推測ではなく確認可能な資料に基づいてレビューするための共通ルールを定義する。
本書は、候補の調査、レビュー台帳への記録、ユーザ承認、正式データへの反映までの手順を対象とする。

日本語名のレビュー中は、候補と確定名を明確に分離する。
Codexは候補の根拠がある場合でも確定扱いにせず、ユーザの明示確認を待つ。

## 日本語名候補の入力ルール

- `proposedNameJa`は、ユーザ確認前の日本語名候補を記録する。
- 公式または信頼できる日本語資料で、対象アドオンとの対応を確認できた場合のみ入力する。
- 英語名、画像ファイル名、文脈からの推測翻訳だけでは入力しない。
- 対象キラー、英語名、画像などを照合し、同名項目や別項目との取り違えがないことを確認する。
- 確認できない場合は`TODO_日本語名確認`のままにする。
- 候補を入力した後も`reviewStatus`は`pending`のままとする。

## 各フィールドの役割

### `proposedNameJa`

- ユーザ確認前の日本語名候補を保持する。
- 調査資料に記載された表記を候補として記録する。
- ユーザ承認前のため、公開用の確定名として使用しない。
- 根拠が不足している場合は`TODO_日本語名確認`を保持する。

### `finalNameJa`

- ユーザ確認後に確定した日本語名を保持する。
- Codexが独自判断で入力しない。
- `reviewStatus: "approved"`にする場合のみ入力する。
- `approved`にする際は、承認された`proposedNameJa`またはユーザが指定した修正版を入力する。

### `reviewStatus`

- 初期値は`pending`とする。
- 日本語名候補を入力した後も`pending`を維持する。
- ユーザが候補と根拠を確認し、問題ないと判断した場合のみ`approved`とする。
- 修正が必要な状態として`needs_fix`などを将来追加することは提案できるが、値の定義と運用が承認されるまで既存データへ追加しない。
- `approved`への変更は、`finalNameJa`の入力と同じ承認作業内で行う。

### `confidence`

| 値 | 基準 |
|---|---|
| `high` | 信頼できる日本語資料で、対象と表記を明確に確認できる |
| `medium` | 候補として有力だが、資料の更新時期や対応関係についてユーザ確認が必要 |
| `low` | 古い資料、表記揺れ、対応関係の不確実さなど、根拠が弱い |

判断不能の場合は`proposedNameJa`を`TODO_日本語名確認`とする。
`confidence`は候補の確定状態を表す値ではなく、根拠の強さを示す補助情報である。
`high`であっても、ユーザ承認前は`reviewStatus: "pending"`とする。

### `notes`

候補を入力する場合は、確認経緯を後から追跡できるよう、可能な範囲で以下を記録する。

- 参照した資料名、ページ名、URL
- 確認日、資料の更新日、対象ゲームバージョン
- 表記揺れや旧表記
- 英語名との対応
- 古い情報である可能性
- ユーザ確認が必要な理由

URLを記録できない場合も、「公式日本語パッチノート」などの曖昧な総称だけで終わらせず、文書名、ページ名、対象項目を特定できる情報を残す。

## 日本語資料の扱い

資料は、原則として以下の優先順位で確認する。

1. 現行ゲーム内の日本語表示
2. Dead by Daylightの公式日本語サイト、公式パッチノート、公式サポート資料
3. 公式配信、公式告知など、対象名を直接確認できる日本語資料
4. 更新履歴と出典を確認できる日本語Wikiやデータベース
5. その他の日本語コミュニティ資料

- 上位資料で確認できる場合は、その表記を優先候補とする。
- 非公式資料は候補調査に利用できるが、公式表記と同等の確定根拠にはしない。
- 資料の更新日や対象バージョンが不明な場合は、`confidence`を下げ、`notes`へ注意点を記録する。
- 複数資料が同じ表記でも、相互転載の可能性がある場合は独立した複数根拠として数えない。
- 英語資料は英語名との対応確認に利用できるが、日本語名そのものの根拠にはしない。

## 推測翻訳の禁止

- 英語名をCodexが直訳または意訳しただけの日本語名を候補として入力しない。
- 画像ファイル名、`id`、アイコンの見た目だけから日本語名を作らない。
- 過去作、原作作品、一般名称の日本語訳が存在しても、ゲーム内表記を確認できなければ採用しない。
- 読みや意味が明白に見える場合も、確認資料がなければ`TODO_日本語名確認`を維持する。

## 表記揺れがある場合

- 句読点、記号、全角半角、スペース、中黒、長音、固有名詞の表記を含め、資料間の差異を勝手に統一しない。
- 現行の公式日本語表示を確認できる場合は、それを優先候補とする。
- 旧表記と現行表記が確認できる場合は、現行表記を`proposedNameJa`へ記録し、旧表記を`notes`へ残す。
- どの表記が現行か判断できない場合は、有力な表記を候補にして`confidence: "low"`または`medium`とするか、`TODO_日本語名確認`を維持する。
- ソース間で候補が矛盾する場合は、両方の資料と表記を`notes`へ記録し、ユーザ判断を待つ。

## 日本語名を確認できない場合

以下を維持する。

```json
{
  "proposedNameJa": "TODO_日本語名確認",
  "confidence": "low",
  "reviewStatus": "pending",
  "finalNameJa": ""
}
```

`notes`には、確認した資料、確認できなかった理由、追加で必要な確認方法を記録する。
候補がないことを理由に、英語名や機械翻訳を日本語名欄へ代入しない。

## ユーザ承認後の確定手順

1. `proposedNameJa`、`confidence`、`notes`を提示する。
2. ユーザが候補表記と根拠を確認する。
3. 修正指示がある場合は、候補と`notes`を修正し、`pending`のまま再確認する。
4. ユーザが明示承認した場合、承認された表記を`finalNameJa`へ入力する。
5. 同じ作業で`reviewStatus`を`approved`へ変更する。
6. JSONとMarkdownの対応行を同期し、件数、ID、確定名、状態を検証する。
7. 正式表示データへの反映は別作業とし、対象と公開可否について改めてユーザ承認を得る。

一括承認を行う場合も、対象キラー、対象ID、承認件数を明示する。
承認範囲が不明な指示から、未指定項目まで`approved`にしない。

## レビュー台帳への反映手順

正本となるレビュー台帳は以下とする。

- `docs/data/addon-review-list.json`
- `docs/data/addon-review-list.md`

候補調査時は、対象をキラーまたは明示されたIDに限定し、以下を同期する。

1. JSONの`proposedNameJa`、`confidence`、`notes`を更新する。
2. Markdownの対応する日本語名候補、`confidence`、`notes`を更新する。
3. 候補入力だけの場合は`reviewStatus: "pending"`を維持する。
4. `finalNameJa`はユーザ承認まで空欄を維持する。
5. `id`、`killerId`、`sourceFileName`、`imagePath`は日本語名レビューを理由に変更しない。
6. 対象外のキラーとアドオンに差分がないことを確認する。

正式確定時は、ユーザが承認した対象だけについてJSONとMarkdownの`finalNameJa`および`reviewStatus`を同期する。

## `src/data`へ移す時の注意

- `src/data`は、ユーザが公開を承認した表示用コピーだけを保持する。
- `proposedNameJa`を公開名として直接転記しない。
- `reviewStatus: "approved"`かつ`finalNameJa`が入力済みの項目だけを反映候補とする。
- `pending`、`TODO_日本語名確認`、表記矛盾、未解決の`notes`がある項目は移さない。
- docsと`src/data`が矛盾する場合は実装を停止し、ユーザへ確認する。
- 公開データへ移した後も、画像の`id`やパスと日本語表示名を分離して管理する。
- ゲーム更新で名称が変わった場合は、先にレビュー台帳と本ポリシーに沿って再確認し、承認後に表示用コピーを更新する。
