# コンポーネント方針

## 目的

React移行の初期実装で使用する共通コンポーネントの責務、状態表示、アクセシビリティ方針を定義する。

## 基本原則

- コンポーネントは表示責務に集中する。
- 大会ルールの意味をコンポーネント内で決定しない。
- 公開データを推測で補完しない。
- 同じ状態と操作は全ページで同じ見た目と文言にする。
- 過度な抽象化を避け、初期3ページで実際に必要な単位だけを作る。

## デザイン参考資料との関係

- 全体方針と参照順序は`DESIGN.md`および`docs/ui/design-references.md`に従う。
- 色、背景色、強調色、警告色、状態色の候補は`docs/DESIGN-cohere.md`を優先して参照する。
- フォント、余白、雰囲気、質感、演出方向は`docs/DESIGN-claude.md`を優先して参照する。
- getdesign由来の具体的なコンポーネント指示は`docs/ui/getdesign-implementation-instructions.md`の対象画面と適用範囲内で参照する。
- 参考資料のコンポーネント名や値を、そのまま本サイトの確定仕様として扱わない。
- 参考資料間または既存仕様との矛盾がある場合は実装せず、矛盾点を整理してユーザへ確認する。
- getdesign指示を反映した場合は、該当コンポーネントの仕様または変更履歴へ反映する。

## PageLayout

責務:

- 共通ヘッダー
- ナビゲーション
- 本文領域
- フッター
- ページ全体の最大幅と余白

ページ固有のルール文言は保持しない。

## SiteHeader

責務:

- サイト名の「そらふぇす」
- サイトの短い説明
- 必要に応じたトップページ導線

`SiteHeader`には大会シリーズ名や開催回名を直接固定表示しない。
大会名は、トップページ、大会カード、大会詳細、ルールページ側で対象となる開催回名を扱う。
現在の開催回名は「ふろぐCup Vol.1」とする。
開催日時やルール状態など、頻繁に変わる情報も直接埋め込まない。

## SiteNavigation

責務:

- 公開中ページへの主要導線
- 現在位置の識別
- キーボード操作可能なリンク

初期項目はHomeとRulesに限定する。
スマホナビ形式は実装前に決定する。

## SiteFooter

責務:

- サイトの補足情報
- 必要に応じた問い合わせ・権利表記への導線

問い合わせ先や外部リンクは、公開先が承認されるまで追加しない。

## ContentCard

責務:

- 関連する情報を視覚的にまとめる
- 見出し、状態、本文、補足、導線を配置する

カードを多用して情報階層を失わないようにする。

## StatusBadge

責務:

- `status`を日本語ラベルとして表示する
- 色以外の文字情報を提供する

初期表示候補:

| status | 表示 |
|---|---|
| `confirmed` | 確定 |
| `under-review` | 検討中 |
| `planned-change` | 変更予定 |
| `undecided` | 未定 |

使用可否は別のラベルまたは本文として表示する。

| availability | 表示 |
|---|---|
| `allowed` | 使用可 |
| `banned` | 使用禁止 |
| `conditional` | 条件付き |
| `undecided` | 未定 |

`isPublished: false`の項目に対して`StatusBadge`を表示しない。項目自体を公開対象から除外する。

## NoticeBox

責務:

- 重要事項
- 注意事項
- 検討中事項の補足
- 更新予定の案内

警告色だけに依存せず、見出しまたは種別をテキストで示す。

## RuleSection

責務:

- ルールカテゴリの見出し
- 公開ルール項目の一覧
- 条件と例外の表示
- 必要に応じた状態表示

ルールの並び順は公開仕様に従い、コンポーネントが独自に重要度を判断しない。

## props設計

- 型を明示する。
- 表示文言を`children`や文字列propsとして受け取る場合も、公開承認済みデータから渡す。
- 任意値と未定値を区別する。
- 数値の`0`と値なしを区別する。
- コンポーネント内部で`docs`のファイルを読み込まない。

## 状態と表示色

- 正式配色は未決とする。
- 状態ごとの色を決める際も、文字ラベル、アイコン、枠などを併用する。
- 使用禁止と検討中を同じ色・同じ意味として扱わない。
- コントラスト不足を避ける。

## HTMLセマンティクス

- ページ構造には`header`、`nav`、`main`、`footer`を使用する。
- 情報のまとまりには適切な`section`を使用する。
- 単なる見た目のために見出し要素を選ばない。
- リンクとボタンの役割を混同しない。
- 表形式が適切なデータは表を使用し、レイアウト目的で表を使わない。

## アクセシビリティ

- フォーカス表示を消さない。
- 状態ラベルに意味が分かるテキストを含める。
- クリック領域を小さくしすぎない。
- スクリーンリーダーでページ見出しとナビゲーションを識別できるようにする。
- 動きの強いアニメーションを初期実装へ入れない。

## スタイル責務

- デザイントークン候補は色、余白、角丸、最大幅とする。
- グローバルCSSはリセット、基本文字、背景などに限定する。
- コンポーネント固有スタイルの分割方法は初期実装時に決める。
- CSS Modules、CSS-in-JS、Sassは初期導入しない。

## 初期フェーズで作らないもの

- 汎用モーダル
- ドロップダウンメニュー
- タブ
- 検索フォーム
- キラーカード
- MAPカード
- ポイント表
- 画像コンポーネント

これらは対応ページの公開仕様が決まった時点で追加する。

## 検証項目

- 同じ状態が同じラベルで表示される。
- 非公開項目がDOMへ出力されない。
- ページごとの主見出しが1つである。
- キーボードで主要リンクを操作できる。
- スマホ幅で本文とナビゲーションが崩れない。
